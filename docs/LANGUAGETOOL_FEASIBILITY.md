# LanguageTool feasibility — 2026-10-10

LanguageTool is a promising additional offline checker for Local Writer. The recommended candidate is an English-only Android adaptation of its existing engine and maintained resources, alongside the local neural tagger. This assessment does not establish Android runtime compatibility or improved detection accuracy: the owner requested no tests, and none were run. The installed app remains version 0.1.6 without LanguageTool.

## What it would add

LanguageTool analyzes sentence boundaries, word tokens, part-of-speech readings and context before matching XML patterns and Java rules. Its English module also provides disambiguation, chunking and inflection. Reusing that maintained system would avoid building a growing collection of app-specific phrase exceptions. It remains substantially rule-based and cannot guarantee detection of every grammatical or semantic problem. [Architecture](https://dev.languagetool.org/development-overview), [English module](https://github.com/languagetool-org/languagetool/blob/8a240373a230477fa2cacfbfec626a681df34b9d/languagetool-language-modules/en/src/main/java/org/languagetool/language/English.java).

The cloned English rule pack includes subject/verb agreement patterns; the Java rule list includes article choice, repeated words and punctuation checks. Its spelling module uses Morfologik dictionaries. The sentence-fragment rule group is marked `default="off"` and `tags="picky"`, so normal checking does not promise a fix for the previously missed fragment. Enabling every optional style/fragment rule could add unwanted findings in chat drafts. [English rules](https://github.com/languagetool-org/languagetool/blob/8a240373a230477fa2cacfbfec626a681df34b9d/languagetool-language-modules/en/src/main/resources/org/languagetool/rules/en/grammar.xml).

`JLanguageTool.check()` can run in the app process; HTTP serving is unnecessary. `RuleMatch` supplies a marked range, explanation, rule identity and zero or more replacement choices. That is a better fit for informative correction cards than our current `Edit(begin,end,replacement)` representation. One checker per worker is required because the Java checker is not thread safe. [Java API](https://dev.languagetool.org/java-api), [RuleMatch](https://github.com/languagetool-org/languagetool/blob/8a240373a230477fa2cacfbfec626a681df34b9d/languagetool-core/src/main/java/org/languagetool/rules/RuleMatch.java).

## Android adaptation required

1. **Use core plus English only.** Preserve the tokenizer, POS dictionaries, disambiguator, chunker, synthesizer, XML/Java rules and Morfologik English spelling resources. Explicit American/British language instances avoid all-language discovery. Keep heavyweight optional n-gram indexes out; upstream describes a roughly 8GB download for those. [N-gram documentation](https://dev.languagetool.org/finding-errors-using-n-gram-data).
2. **Prune code and dependencies together.** The 6.8 core POM includes gRPC, OpenTelemetry, Prometheus/Micrometer metrics, JAXB, Lucene and native Hunspell bindings. Dependency presence alone does not establish network sending. The cloned checking code does call a telemetry provider, so the offline fork must remove those hooks and remote-rule paths, not merely disable the HTTP server. Retain only dependencies needed by English checking. [Core POM](https://github.com/languagetool-org/languagetool/blob/e807fcde6a6506191e1470744d2345da28c26be6/languagetool-core/pom.xml), [telemetry provider](https://github.com/languagetool-org/languagetool/blob/8a240373a230477fa2cacfbfec626a681df34b9d/languagetool-core/src/main/java/org/languagetool/tools/TelemetryProvider.java).
3. **Adapt XML parsing.** `PatternRuleLoader` sets JDK-specific SAX entity-limit properties; exceptions abort rule loading. Gate or replace those setters for Android's parser while keeping all rule resources local. Actual parser behavior remains untested. [Loader](https://github.com/languagetool-org/languagetool/blob/8a240373a230477fa2cacfbfec626a681df34b9d/languagetool-core/src/main/java/org/languagetool/rules/patterns/PatternRuleLoader.java).
4. **Package resources deliberately.** Our manual build currently converts dependency classes to DEX but does not copy their Java resources into the APK. Rules, dictionaries, messages and reflected filter classes need explicit packaging. Provide a local Android `ResourceDataBroker` or preserve compatible classpath loading; use app-private files where a resource needs a file URL. [Broker](https://github.com/languagetool-org/languagetool/blob/8a240373a230477fa2cacfbfec626a681df34b9d/languagetool-core/src/main/java/org/languagetool/broker/DefaultResourceDataBroker.java).
5. **Review Java APIs and error logging.** The current source targets Java 17; Android support requires a D8/desugaring and dependency review. Java 17 bytecode alone is not proof of incompatibility. Strip input-bearing exception logging in the offline fork. The inspected snapshot's shorter `inputLogging` constructor overload forwards a literal `true`, so it cannot be trusted to enforce the app's privacy setting. [Checker source](https://github.com/languagetool-org/languagetool/blob/8a240373a230477fa2cacfbfec626a681df34b9d/languagetool-core/src/main/java/org/languagetool/JLanguageTool.java), [Android Java API guidance](https://developer.android.com/build/jdks).

The community engine is LGPL 2.1 or later; preserve its license and dependency notices in any integration. The hosted AI checks are not included in a local deployment. [Repository](https://github.com/languagetool-org/languagetool), [offline server feature limits](https://dev.languagetool.org/http-server).

## Mapping to Local Writer

Keep the current accessibility capture, UTF-16 bounds, underlines, compact/full panel flow and strict source validation. Add a shared issue representation carrying source, range, rule ID, category, explanation and replacement alternatives. An issue without a replacement is reviewable/dismissible but cannot be auto-applied. Merge equal findings from LanguageTool and the tagger, and keep conflicting alternatives explicit rather than blindly applying overlapping edits. Bulk acceptance must select only non-overlapping, actionable choices.

Run one reusable LanguageTool instance on the existing `Engine.worker`; connect its cancellation callback to the current analysis revision. Apply personal dictionary and dialect preferences consistently. Start with the normal grammar/spelling rule set, keep style rules optional, and continue model checking for additional cases. The manifest should retain no Internet permission; no login or telemetry components are needed for this design.

Next implementation work is a pinned English-only compatibility fork, dependency/resource packaging, then the issue adapter and panel metadata. Compilation can establish build compatibility; the owner will assess phone memory, latency, false positives and whether the combined checker catches more real errors. None of those measurements has been performed in this investigation.
